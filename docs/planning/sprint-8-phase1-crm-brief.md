## 3. Sprint goal and exit

**Goal.** The **lead-to-subscriber journey (Flow 1, revised)** live and local: a public enquiry creates a `leads` row with source, consent and owner; Sales works it in the team workspace with activities, follow-up reminders, duplicate flagging and a funnel report; a lead **converts** to a `client_accounts` row with a portal invitation; and a subscriber buys the hotel-discovery subscription through **Razorpay sandbox**, whose signed `payment.captured` webhook activates exactly the purchased entitlement — **hotel discovery open, the wedding modules locked** (AC-02). Private data is protected throughout (AC-27 / AC-12 / AC-21).

**Exit (all green under the block's own checks; build each criterion to its P1 + P2 tests):**
- **AC-01** (lead capture) — all nine: website enquiry saves source + consent + notice version and notifies Sales (01.1); demo request sets `requested_demo` + a demo task (01.2); email **or** phone required, E.164 +91 (01.3); manual lead with source + owner + activities (01.4); follow-up reminder fires once, idempotent (01.5); duplicates **flagged, never refused or auto-merged**, merge by Sales with audit (01.6); funnel report correct, HT 404 on the route (01.7); convert → `client_accounts` + invite, lead read-only, edit 409 (01.8); form rate-limited + bot-checked, 429/400, no lead created (01.9).
- **AC-02** (subscription gating) — purchase activates only the purchased modules (02.1); wedding endpoints **absent** for a subscriber-only account, empty list + 404 records (02.2); failed payment grants nothing (02.3); manual bank transfer activates through the same step (02.4); duplicate webhook processed once (02.5); bad signature rejected 401 (02.6); expiry removes subscription modules only, nothing deleted (02.7); plan price/inclusions are configuration, CI finds no hard-coded price (02.9); no self-registration route (02.10); renewal restores access + data (02.11).
- **Privacy / protection:** AC-27.1 (consent + notice version stored, history immutable), AC-27.5 (no personal data in logs), AC-12 (generated authz suite covers every row; denial = absence; no restricted field in any client response), AC-21 (audit on convert, merge, manual payment, restricted reads).
- `pnpm check` **green**; the **generated authorisation suite** green; a **contract test** for the Razorpay adapter against its sandbox; component tests for PUB-06 and the portal purchase screen with all four states + accessibility (AC-16); no hard-coded price/fee/colour/string (`code.md`, AC-25.4).
- Every new pattern/dependency carries a **D-record**; **no external account blocks the sprint** (sandbox + stubs stand in; live paths gated on §2 decisions 1–2).

## 5. The features, in order

Each endpoint follows the CONTRIBUTING order: **Zod schema (`packages/core/src/schemas/<domain>.ts`) → permission key (`packages/policy`) → Prisma model + migration → controller (thin) → service (rule + `decide()`/`canTransition()`) → repository (`projectScope`/account scope, demo flag, visibility, soft delete) → `packages/api-client` hook → screen from `packages/ui` → tests next to code.** Response envelope `{ data }` / `{ error }`; one response model per audience; **every lead field is INTERNAL and never serialised to a client/guest/demo/public principal.**

### 8.1 Lead capture — the public enquiry, the team workspace, follow-up, duplicates, funnel *(this sprint's headline; delivers the first viewable screen)*

- **Why first:** it is the entry of Flow 1, it is pure Module B + kernel (no payments), and **PUB-06 on the public website (`apps/web`) is the earliest runnable, viewable surface** — a visitor submits an enquiry and it becomes a `leads` row. Satisfies **AC-01** (all nine sub-tests).
- **Entities (`data-model.md` §4):** `lead_sources` (reference, `source_key` website/instagram/advertisement/referral/call/other), `leads` (the enquiry/pipeline record), `lead_activities` (append log; `next_follow_up_at` drives the reminder). All three carry the standard columns + soft delete; none is partitioned.
- **Contract (`packages/core/src/schemas/leads.ts`):** `leadEnquiryRequest` (public: name required; **email or phone required, not both**; phone E.164 default +91; email lowercased; optional contact_preference, tentative dates (to not before from), destination_id *or* destination_text, guest_estimate ≥0, requirements ≤10 000, requested_demo, **consent_marketing + the notice version**); `leadCreateRequest` (staff, adds source + owner); `leadUpdateRequest`, `leadView` (internal), `leadActivityCreateRequest`, `leadActivityView`, `leadFunnelQuery`/`leadFunnelView`. Reuse `common.ts` (`uuid`, `cursorQuery`, `page`).
- **Permission (`packages/policy`):** use `crm.leads.{create,read,update,delete}` (SA/SM CRUD, HT/PM read, scope **all**; `lead_activities` covered by the same row) and the §5.16 **lead-source-and-conversion-funnel** report key (run/export: SA, SM — HT must 404). The public enquiry is a **system-principal** write (no permission key; `client/guest/demo` never touch leads). Confirm keys in `matrix.json`; `pnpm authz:generate`.
- **States / rules:** `leads.status` = `new → contacted → introduction_shared → demo_offered → demo_accessed → follow_up → converted → closed`; `owner_user_id` required before `contacted` (and set only by SM/SA, never the public form); `closed_reason` required before `closed`; `converted` is **SYS-only** and makes the lead read-only (edit → 409, AC-01.8, built fully in 8.2). `canTransition()`-guard every change. Enum in code, labels in config.
- **Build:**
  - **Public enquiry endpoint** (system principal): rate-limit per IP + per form and a **bot-check** (adapter + config, `security.md`/§11; 429 over the limit, 400 without a valid token — AC-01.9); validate at the edge; write the `leads` row `status=new`, `owner` unassigned, `source_id` from `lead_sources`, **consent_marketing + consent_at + notice version**; **duplicate flagging** (match incoming email/phone against existing `leads` + `client_accounts`, flag for Sales, **never refuse or auto-merge** — AC-01.6); emit a domain event → **in-app notification to Sales** ("enquiry received"); respond for **PUB-09** with no echoed data beyond the first name.
  - **Team workspace API** (staff): list (cursor-paginated, filter by source/owner/destination/status/date) for **TW-10**, detail + activities timeline for **TW-11**, create manual lead (AC-01.4), add activity (with `next_follow_up_at`), assign/bulk-assign owner, close (reason), **merge duplicate** (SM picks survivor; activities move; duplicate `closed_reason='merged'`; **audited** — AC-01.6/AC-21).
  - **Follow-up reminder job** (reuse the job seam + `job_runs`, worker-only, D-047; model on `session-reaper`): scan `lead_activities.next_follow_up_at`, send **one** in-app notification to the lead owner with the lead link, **idempotent** on re-run (AC-01.5).
  - **Funnel report** (`crm` §5.16): counts by source and status; **HT 404** on the route (AC-01.7).
  - **api-client hooks** (`packages/api-client`): the public submit + the staff list/detail/activity/convert hooks.
  - **Screens (viewable):** **PUB-06** enquiry form in `apps/web/src/app` (public, Next.js) from `packages/ui` form components — single column, grouped sections, inline validation, consent notice (configurable text), bot check, privacy-notice link; all four states + accessibility (AC-16/AC-26); **PUB-09** thank-you. (TW-10/TW-11 are Expo team-app screens; this sprint ships the **API + the public PUB-06 screen** as the viewable surface — the native workspace screens can follow with 8.2 so the slice stays runnable without the mobile build if time is short.)
- **Tests:** Vitest for the service (duplicate flag, status guards, consent capture, reminder idempotency) + `core` schema (email-or-phone, E.164) + the funnel; supertest e2e (201 create; 400 naming the field; 429/400 abuse; HT 404 funnel; denial = absence); RNTL/web component tests for PUB-06 states + a11y; a bot-check adapter contract test.
- **Local↔live:** in-app notifications now → WhatsApp/SMS via the adapter + switch when decision 1 lands; bot-check vendor keys are an (AMPM) live input.

### 8.2 Convert lead → client account + portal invite *(AC-01.8)*

- **Why:** closes the lead loop and creates the subscriber the subscription needs; small on top of 8.1 + the Module-A identity seam.
- **Build:** a `crm.accounts` service — **Convert** (TW-11 action): create `client_accounts` (`status=prospect`, `lead_id` back-link), create the `account_contacts` primary contact, set `leads.converted_account_id` + `converted_at` + `status=converted` (SYS, lead now read-only), and **send the portal invitation** by minting an `auth_tokens` (`purpose='invite'`) for a `users` row (`status=invited`, `user_type=client`) linked via `account_contacts.user_id`, delivered through the notification seam (AUTH-02). Audit the conversion (AC-21). `crm.accounts.*` keys (SA/SM CRUD all; FA billing fields only, RESTRICTED-BANK). `client_accounts.internal_notes` is RESTRICTED-NOTES; billing fields RESTRICTED-BANK — separate response models, never serialised to a client.
- **Tests:** convert creates the account + contact + invite, lead edit → 409; re-convert is a no-op/refused; billing/internal-notes absent from any client view (AC-12.3).

### 8.3 Subscription plans + purchase → Razorpay → activation → entitlement gating *(AC-02)*

- **Why:** the commercial payoff; proves the whole kernel (policy, entitlements, jobs, webhooks, audit) end to end against a real provider sandbox.
- **Entities:** `plans` + `plan_modules` (reference/config; v1 = Discovery, Rs 50 000, `one_time`, one month, `module_key` `hotel_discovery` + `hotel_assistance`; **price is a `configurations`/`plans` value, never code** — AC-02.9/AC-25.4), `subscriptions`, `payments` (`direction=inbound`, `purpose=subscription`, `client_visible=true`).
- **Build:** `CP-11` purchase screen (choose plan + accept terms + **basic wedding details** step, §0a) → `POST /subscriptions` creates `subscription=pending_payment` + `payment=initiated` + a Razorpay **order** → web runs **hosted checkout** (card data never reaches AMPM) → the signed **`payment.captured`** webhook lands on the **worker**, which **verifies the signature + idempotency on `provider_ref`** (AC-02.5/02.6), marks `payment=succeeded`, `subscription=active` (`starts_at`/`ends_at` from the plan), **recomputes entitlements** and audits. A **manual bank-transfer** path (FA, TW-14) runs the **same** activation step (AC-02.4; `activation_source=gateway_webhook|manual`). **Expiry job** (worker): `active → expiring → expired`, removes **subscription** modules only, deletes nothing (AC-02.7). **Entitlement gating** (`entitlements.ts`): an active/trial subscription grants its plan's `plan_modules`; **wedding workspace stays locked** and those Phase-2 modules are not even built — gate at the entitlement layer so a subscriber-only account gets an empty project list + 404 on wedding records (AC-02.2). **No self-registration** (AC-02.10).
- **Adapter + D-record:** one `PaymentAdapter` interface + a `RazorpayPaymentAdapter` behind it, **sandbox** config for dev/staging, a **contract test** against the sandbox in CI (`api.md`); provider SDK never imported by business logic; keys from the secret zone (feature 6.4). **D-record the payment adapter + webhook pattern.**
- **Tests:** the full AC-02 set (sandbox e2e for 02.1/02.11; job tests for expiry; security tests for signature + idempotency + no-self-registration); the generated authz suite for the subscriber rows (AC-02.2/AC-12.1); the no-hard-coded-price CI check.

## 6. Cross-cutting

- **Entitlements are computed, never stored** (`entitlements.ts`, cached ≤5 min). AC-02 is an **entitlement** decision, not a permission key: a subscription payment never grants wedding-workspace, a service agreement never grants hotel search (`permission-matrix.md` §3, line 109).
- **Denial equals absence** (same 404 for forbidden and non-existent); **repository scoping mandatory** on every account/project-owned query (account membership, `is_demo`, visibility, soft delete); no query bypasses the repository.
- **Visibility / money:** every field has one visibility class; **all `leads`/`lead_activities` fields are INTERNAL**; `client_accounts` billing = RESTRICTED-BANK, `internal_notes` = RESTRICTED-NOTES, outbound `payments` = RESTRICTED-FINANCE; `plans`/`plan_modules` = PUBLIC when active. Client-facing and internal amounts are **separate columns + separate response models**; `MoneyText` takes client amounts only. Internal cost/margin/vendor rates never reach a client by any channel (`security.md`, brief rule 8).
- **Consent where data enters** (PUB-06): `consent_marketing` + `consent_at` + the notice version; notice text configurable; **nothing hard-deleted** — retention is a Super-Admin-approved proposal (AC-27).
- **Reuse the seams, don't rebuild:** the follow-up reminder + expiry jobs use `defineJob`/`JobQueue`/`job_runs` (no second scheduler); notifications go through the notification seam (in-app now); cross-module reactions go through **domain events on the worker**, never a direct upward call.
- **Webhooks** verify the provider signature, store the raw event, process through an **idempotent job** keyed on `provider_ref`; **activation happens once per transaction** whatever the notifications.
- **Config, not code:** plans, prices, demo limits, lead sources, consent text, retention periods, thresholds and labels are `configurations`/reference rows read through the typed accessor.
- **Audit** on create/convert/merge/manual-payment/restricted-read; **no personal data in application logs** (AC-27.5); `redact` on the masked path.
- **Pre-merge (every feature):** diff vs `CLAUDE.md` + every rule file, each violation as file:line with the rule; then the invariants no linter sees — scoped repository on every account/project query, every new permission from the matrix, data-model doc and schema agree, migrations expand before they contract, no internal amount in a client view.
