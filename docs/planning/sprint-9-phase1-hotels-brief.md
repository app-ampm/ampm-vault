## 3. Sprint goal and exit

**Goal.** The **hotel database is real and loadable, priced, fresh and browsable** — the substance of Flow 2's discovery half. Eva can load ~200 hotels (rooms, venues, rates, menus) from a **frozen spreadsheet template** through a validating import that creates **unverified** rate cards; the Hotel team verifies cards against a recorded verification so a hotel page shows room categories, venue capacities and **indicative per-plate / wedding-package / venue-rental / room-rate ranges** stamped **"Verified on \<date\> by AMPM"** (or **"Stale, last checked \<date\>"**, or **"Rates on request"** when unverified — and **never** "confirmed"); photos and consented previous-wedding references load through a safe media pipeline with signed links; and a subscriber searches and filters destinations and hotels, opens a rich detail page with maps/street view, and saves and compares — at p95 under 400 ms over 500 hotels. Private data (internal rating/notes, rate source, hotel contacts) is protected throughout.

**Exit (all green under the block's own checks; build each criterion to its P1 + P2 tests):**
- **AC-35.1** (hotel import) — upload the template with hotels, rooms, venues and rates including invalid rows; the **validation report names the rows and fields**; apply creates the valid hotels with **unverified** rate cards; **audit events per row**; the `job_runs`/`import_jobs` record stores counts and the error report.
- **AC-04** (freshness) — all seven: 04.1 verified→"Verified on \<date\>", after the job→`stale`/"Stale, last checked \<date\>", amounts still shown, the **word "confirmed" never appears in rate context** (asserted by text search of page **and** API); 04.2 a card with no verification → "Rates on request" + the assistance action, **no amounts** in the response; 04.3 the freshness job sets `stale`, denormalises `hotels.last_verified_at`, notifies HT **once**, idempotent on re-run; 04.4 setting a card `verified` with no `verification_id` → **409**, succeeds after a verification is recorded; 04.5 search filters/exclusions exact (capacity ≥ N, verified-rates-only, destination), **inactive never returned**, destination counts match; 04.6 p95 < 400 ms search / < 600 ms detail at 500 hotels (k6); 04.7 availability labelled **separately** from rates, no calendar implied.
- **AC-20 / AC-24** (media) — expiring signed links; upload type/size limits; **AV scan** (fail-closed); image metadata stripping and derivatives; access follows the owning record; controlled video delivery; previous-wedding references **refuse client/public visibility without consent** (GP-20).
- **AC-34.1** (search load) — the §6 search profile holds at the 200–500-hotel scale.
- **Privacy / protection:** AC-12 (generated authz suite covers every new row; denial = absence; **no RESTRICTED field — internal rating/notes, rate source, `hotel_contacts` — in any client/demo/public response**), AC-21 (audit on verify, import apply per row, restricted reads, reference-consent changes), AC-16/AC-26 on the client discovery screens.
- `pnpm check` **green**; the **generated authorisation suite** green (`pnpm authz:generate`, no drift); **no hard-coded price/fee/colour/string** (`code.md`, AC-25.4 — all amounts are data, all labels are config); every new pattern/dependency carries a **D-record**; **no external account blocks the sprint** (local store + stub scanner + plain uploads stand in; live paths gated on §2 and the appendix).
- **The import template is frozen and handed to Eva** (the week-8 "format agreed + 10 samples" commitment — delivered from 9.1).

## 5. The features, in order

Each endpoint follows the CONTRIBUTING order: **Zod schema (`packages/core/src/schemas/hotels.ts` — extend the existing file) → permission key (`packages/policy`) → Prisma model + migration → controller (thin) → service (rule + `decide()`/`canTransition()`) → repository (entitlement + `demo_visible` + visibility + soft delete scoping) → `packages/api-client` hook → screen from `packages/ui` → tests next to code.** Response envelope `{ data }` / `{ error }`; one response model per audience; **every RESTRICTED hotel field is absent from client/demo/public responses.**

### 9.2 Rate cards + rate items + verifications + the freshness job *(the commercial heart; AC-04)*

- **Why:** this is Q9's substance — indicative pricing with a last-verified date — and the content Eva verifies for the week-20 full DB. **Lock R8 and R9 here** (they govern chargeable flags and cost visibility).

## 6. Cross-cutting

- **Entitlement, not just permission:** hotel discovery is gated by the computed `hotel_discovery` entitlement (`entitlements.ts`), cached ≤ 5 min; an active/trial subscription grants it, an expired one leaves saved **names** only. A subscription never grants the wedding workspace.
- **Denial equals absence** (same 404 for forbidden and non-existent); **repository scoping mandatory** on every query (entitlement, `demo_visible`, visibility class, soft delete); no query bypasses the repository.
- **Visibility / money:** every field has one visibility class. **RESTRICTED** — `hotels.internal_rating`/`internal_notes`, `rate_cards.source`/`internal_notes`, the whole of `hotel_contacts` — is never serialised to client/demo/public. **CLIENT** — profiles, rooms, venues, **verified** rate items marked `client_visible`, consented references. **PUBLIC** — `destinations.public_visible` and `hotels.public_showcase` expose name/destination/hero media only. Amounts are indicative **ranges** (`amount`/`amount_max`); confirmed quotations are Module D.
- **Freshness is the product's integrity:** the stale label and the "never confirmed" rule are acceptance criteria, not polish (AC-04). The freshness job is the only writer of `stale`/`last_verified_at`.
- **Config, not code:** `hotel_verification_max_age_days`, hotel/venue categories, demo curation, media size/type limits, and every label are `configurations`/reference rows read through the typed accessor. No hard-coded price, fee, category, colour or string.
- **Reuse the seams, don't rebuild:** the freshness + import jobs use `defineJob`/`JobQueue`/`job_runs` (no second scheduler); notifications go through the notification seam (in-app now); cross-module reactions go through domain events on the worker, never a direct upward call; `media_assets` is the Module-N table, not a hotels-local copy.
- **Audit** on verify, import apply (per row), restricted reads, and reference-consent changes; **no personal data in logs** (`redact`).
- **Pre-merge (every feature):** diff vs `CLAUDE.md` + every rule file, each violation as file:line with the rule; then the invariants no linter sees — scoped repository on every hotel query, every new permission from the matrix, data-model doc and schema agree, migrations expand before they contract, no RESTRICTED field in a client view, no amount on an unverified card in a client response.
