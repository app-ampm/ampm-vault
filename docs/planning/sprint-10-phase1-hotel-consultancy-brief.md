## 3. Sprint goal and exit

**Goal.** The **hotel consultancy pipeline is real and private.** A subscriber (or a client with an active hotel-assistance agreement) raises an enquiry about a discovered hotel; the Hotel team runs it through the ten-status pipeline — availability → (paid agreement where chargeable) → negotiation → site visit → a **versioned proposal carrying separate client and internal totals** → booking milestones — reaching **`confirmed` only on a completed `confirmed` milestone and a signed contract**; the client tracks status, accepts/declines proposals seeing **client amounts only**, and submits site-visit feedback; **every internal note, internal total, hotel contact and internal outcome is ABSENT from — not masked in — client responses**; a **demo prospect's request becomes a Sales lead activity, never an enquiry** (P-7). API-first; the polished client and team screens follow visual-design approvals (build-plan sprints 20–24).

**Exit (all green under the block's own checks; build each criterion to its P1 + P2 tests):**
- **AC-05.1–.8** (the internal/client separation across the whole flow): 05.1 internal-only events absent from the client timeline; 05.2 `notes_internal`, `outcome_internal`, `internal_total_amount`, `assigned_user_id`, `service_agreement_id` and hotel contacts never serialise — client schemas assert `additionalProperties: false` over **every** enquiry/visit/proposal route; 05.3 client-visible transitions send **exactly one** client notification each; 05.4 "Preview as client" is **byte-identical** to the real client response; 05.5 site-visit feedback round-trips, `outcome_internal` absent; 05.6 `confirmed` needs a done `confirmed` milestone **and** a signed contract → **409 naming the missing item** otherwise; 05.7 chargeable services **wait for an active agreement** → 409 until `service_agreements.status = active`, availability allowed throughout; 05.8 hotel contacts (phone/email) never in any client response.
- **AC-03.4** (demo → Sales activity, P-7): a demo prospect's CP-07 creates **no** `hotel_enquiries` row, writes a `lead_activities` row of type `demo` on the originating lead, notifies the lead owner, and leaves the TW-26 queue unchanged. (Verify the C-built path; add the subscriber branch that *does* create enquiries.)
- **AC-26.1/.2** (CP-07 entry): a double-submit / replay with the same idempotency key creates **one** record set; a single multi-hotel request creates several enquiries but never duplicates; per-step draft recovery after refresh, cleared on submit.
- **AC-31.1** (generated transition tests): for every `permission-matrix` §7 enquiry transition, listed principals succeed, an unlisted principal gets **403**, an unlisted transition gets **409** with the guard message, and each success writes an `audit_events` row (§9) **and** the configured notifications (§8). **Plus an explicit `hotel_proposals` status-machine AC** (`draft→shared→revision_requested→accepted→declined→superseded`, shared versions immutable, audit on share/accept/decline) — the gap the design docs leave for this brief to close.
- **AC-04.1 / AC-04.7** (carried from C): the word **"confirmed" never appears in a rate context** — confirmed quotations exist only in `hotel_proposals`; date-specific availability is answered **inside an enquiry**, never a calendar.
- **Privacy / protection:** AC-12 (the generated authz suite covers every new row; denial = absence; **no RESTRICTED-FINANCE (`internal_total_amount`), RESTRICTED-NOTES (`notes_internal`, `internal_only` events, `outcome_internal`) or RESTRICTED-CONTACT field in any client/demo response**); AC-21 (audit on create/update/**share**/**accept**/**decline**/close, `service_agreement` status changes, and every RESTRICTED-FINANCE read by a Super Admin outside Finance); no personal data in logs (`redact`).
- `pnpm check` **green**; the **generated authorisation suite** green (`pnpm authz:generate`, no drift) with the §5.4 slugs **curated** off `provisional`; **no hard-coded price/fee/colour/string** (fees are entered, chargeable-flags are config); every new pattern/dependency carries a **D-record**; **no external account blocks the sprint** (in-app notifications; **offline bank-transfer** milestones — no payment-gateway job in v1; local document store).

## 5. The features, in order

Each endpoint follows the CONTRIBUTING order: **Zod schema (`packages/core/src/schemas/consultancy.ts`, new file; import the existing shared `item_type` from `hotel-rates.ts`) → permission key (`packages/policy`, curate the provisional slug) → Prisma model + migration → controller (thin) → service (rule + `decide()`/`canTransition()`) → repository (entitlement + account/project membership + visibility + soft-delete scoping) → `packages/api-client` hook → screen from `packages/ui` → tests next to code.** Response envelope `{ data }` / `{ error }`; **one response model per audience**; **every RESTRICTED field is absent from client/demo responses.** Screens are API-first this sprint: wire a thin staff/client harness where useful; the polished CP-07/08/09/10 and TW-15/26/27/28 screens follow design approvals (build-plan 20–24).

- **Why first:** `hotel_enquiries` is the root every other Module D row hangs off, and it is the one feature with no dependency on agreements or proposals. It closes the CP-07 boundary Module C deliberately stopped at.
- **Entities (`data-model.md` §6):** `hotel_enquiries` (FKs `account_id`→client_accounts, `project_id`→wedding_projects **nullable** GP-27, `hotel_id`→hotels [C], `requested_by_user_id`/`assigned_user_id`→users, `service_agreement_id`→service_agreements [B] **nullable** GP-5; `date_from/to`, `dates_flexible`, `guest_estimate`, `rooms_required`, `functions_summary` **CLIENT**, `contact_preference`, `notes_client` **CLIENT**, `notes_internal` **RESTRICTED-NOTES**, `submitted_at`, `closed_at`; **status** enum 10 (`draft → submitted → awaiting_hotel → response_received → negotiating → visit_scheduled → proposal_received → client_decision → confirmed → closed`), **outcome** enum 4 (`booked | declined | no_availability | withdrawn`) — a *separate* terminal column set on close); `hotel_enquiry_events` (`event_type` enum 8 (`submitted | sent_to_hotel | hotel_response | negotiation_note | client_update | status_change | visit | proposal`), `internal_only` bool — **row-level** hide-from-client, `summary`, `occurred_at`, `user_id`, `document_id`; append-only per §2.5). Standard columns + soft delete. **This feature also builds the minimal `documents` + `document_access_links` layer** over the storage port (the first `document_id` consumer, §1).
- **Permission (`packages/policy`):** curate `consultancy.enquiries.*` (+ `read` of client fields vs the RESTRICTED `enquiry_notes` sub-resource) and `consultancy.enquiry_events.*`. Role matrix (§5.4): **SA** CRUD; **HT** CRU (operational owner, drives all transitions); **SM** create+read (owns the later agreement step, no internal notes beyond read); **PM** the `:assigned` variant; **FA** read; **CD/VC/RG/HL** none. **Client (CR)** create+read **own** requests, read status + non-internal events, update own `notes_client`.
- **States / rules:** the enquiry status graph (`permission-matrix` §7) — `draft→submitted` (CR, or SM/HT on behalf); `submitted→awaiting_hotel→response_received` (HT); `response_received→negotiating` (HT, **guard: chargeable → 409 until an active agreement**, 10.2); `→visit_scheduled` (HT, PM(a)); `→proposal_received` (HT); `proposal_received→client_decision` (HT, PM(a), only when a proposal is shared); `client_decision→confirmed` (HT, SA, **guard: done `confirmed` milestone + signed contract**, 10.5); `any→closed` (HT, SA, PM(a), requires an `outcome`). `canTransition()` holds the graph; data-dependent guards return **409 naming the missing item**. **Entitlement:** gate the subscriber create path on the `hotel_assistance` reach entitlement; a **demo prospect** short-circuits to a `lead_activities` row (P-7), **no enquiry**. CP-07 submit is **idempotent** on an idempotency key (AC-26.1); a multi-hotel request creates one enquiry per hotel, the requested services in the first event.
- **Tests:** Vitest for the service (status-machine transitions + guards, the client/internal serialiser dropping `notes_internal` and `internal_only` events); `core` schema (enquiry create/validation, `additionalProperties:false` client view); supertest e2e for AC-05.1/.2/.3/.4, AC-26.1/.2, AC-03.4 (demo→lead activity), and the AC-31.1 generated transition rows for `hotel_enquiries`; authz-suite rows (denial = absence; no RESTRICTED field in a client response).

### 10.2 Service agreements — the chargeable-services gate *(Module B, first used here; AC-05.7)*

- **Why here:** the `negotiating` transition and every chargeable service are blocked until an active agreement exists, so the gate must exist before negotiation/visits/proposals. R8 is locked here.
- **Entities (`data-model.md` §4):** `service_types` (`service_key` enum, `category = hotel_assistance | …`) and `service_agreements` (`account_id`, `project_id` **nullable**, `service_type_id`, `hotel_enquiry_id` **nullable** — the reciprocal of `hotel_enquiries.service_agreement_id`, GP-5; `scope_text`, `fee_amount` **entered, never defaulted from code**, `fee_structure` enum `fixed|percentage|milestones`, `currency`, `terms_version`, `status` enum `draft→sent→accepted→active→completed→cancelled`, `accepted_at`, `accepted_by_user_id`, `document_id`). Standard columns + soft delete.
- **Permission:** `crm.service_agreements.*` is already a stable, curated §5.2 resource (reuse it) — **SA** CRUD, **SM** CRU (create/read/update, **no delete**), **HT** CRU limited to hotel-category services (grant conditioned `subject anyOf = hotel`), **PM** `:assigned` RU, **FA** read; clients **accept** their own agreement (read + an `accept` action).
- **States / rules:** which `service_key`s require an agreement is **config** (R8 default: availability included, the rest chargeable). The chargeable guard in 10.1 reads `service_agreements.status = active` for the enquiry before allowing `negotiating`; **availability checks proceed without one**. - **Tests:** service Vitest (the config-driven chargeable gate, the status machine, the reciprocal FK link); e2e for AC-05.7 (409 before active, success after); authz rows.

### 10.3 Site visits *(AC-05.5)*

- **Why:** a small, self-contained step that proves the internal/client split on a second table before the proposal (the hardest one).
- **Entities (`data-model.md` §6):** `site_visits` (`enquiry_id`, `hotel_id` [C], `scheduled_at`, `status` enum `proposed|confirmed|completed|cancelled`, `attendees_text` INTERNAL, `outcome_internal` **RESTRICTED-NOTES**, `client_feedback` **CLIENT**). Standard columns + soft delete.
- **Permission:** curate `consultancy.site_visits.*` — SA/HT CRU, PM(a), SM read; the client reads the visit date/status and **submits/updates their own `client_feedback`**.
- **States / rules:** scheduling moves the enquiry to `visit_scheduled` (10.1 guard); completion records `outcome_internal` (never client-visible); attendees are reminded via the notification seam; the client view carries date + status + own feedback only.
- **Tests:** e2e AC-05.5 (schedule → complete with `outcome_internal` → client feedback; `outcome_internal` absent from the client view); authz rows.

### 10.4 Hotel proposals + lines + the version/decision machine *(the commercial heart; AC-05.2 totals, the proposal status-machine AC, AC-09 version lock)*

- **Why:** the negotiated offer is where client and internal money meet and must stay in **separate columns** (A-4); the whole module's privacy guarantee lives or dies here. R9 is locked before this.
- **Entities (`data-model.md` §6):** `hotel_proposals` (`enquiry_id`, `hotel_id` [C], `version_number`, `status` enum `draft|shared|revision_requested|accepted|declined|superseded`, `valid_until`, **`client_total_amount` CLIENT (A-4)**, **`internal_total_amount` RESTRICTED-FINANCE** ("hotel net / commission basis"), `currency`, `document_id`, `shared_at`, `decided_at`, `decided_by_user_id`, `approval_id`→approvals [I] **nullable** §2.3, `supersedes_proposal_id` self-ref); `hotel_proposal_lines` (`proposal_id`, shared `item_type` enum, `description`, `quantity`, `unit_amount`, `total_amount`, `client_visible` bool — per-line). **Margin is DERIVED** (`client_total − internal_total`); do **not** add a margin/commission/vendor-cost column. Standard columns + soft delete.
- **Permission:** curate `consultancy.proposals.*` with a distinct **`read_internal_amount`** sub-action and a **`share`** action. `client_total_amount` + `client_visible` lines readable by the client reps; **`internal_total_amount` readable only by SA/FA/HT/PM(a)** (R9). Two response models: `HotelProposalClientView` (client amounts + `client_visible` lines only) and `HotelProposalInternalView` — a field outside the principal's classes **is not serialised at all**, never a hide-flag.
- **States / rules:** `draft→shared` (creates the version lock; notifies; the client now sees it in CP-10 with client amounts only) `→revision_requested` (client asks, new version **supersedes** the prior, shared versions **immutable** → 409 on edit, AC-09.x) `→accepted|declined` (the client decision). **Sharing** a proposal drives the enquiry `proposal_received→client_decision` (§7); an **accepted** proposal then drives `client_decision→confirmed` once the `confirmed` milestone and a contract exist. Expired `valid_until` disables the decision. Interim version-immutability is enforced in-service (approvals integration deferred). Emits `proposal.shared/accepted/declined/expired` events on the worker; **proposal expiry** surfaces via a new reminder job (§1 pattern).
- **Tests:** service Vitest (the version/supersede chain, immutability of shared versions, the two serialisers); `core` schema (client view `additionalProperties:false` rejects `internal_total_amount`); e2e for AC-05.2 (internal total never serialises on any client route) and the **explicit proposal status-machine AC** (share/accept/decline/supersede + audit); authz rows for `read_internal_amount` (SM/CD/VC/RG/HL denied).

### 10.5 Booking milestones + the confirmed guard *(AC-05.6)*

- **Why last:** it depends on an accepted proposal and closes the pipeline; its `confirmed` milestone is what flips the enquiry to `confirmed`.
- **Entities (`data-model.md` §6):** `booking_milestones` (`enquiry_id`, `project_id` **nullable**, `milestone_type` enum `hold_placed|contract_sent|contract_signed|advance_paid|rooming_list_due|balance_due|confirmed`, `due_at`, `completed_at`, `status` enum `pending|done|overdue|cancelled`, **single `amount`** column + `currency`, `contract_id`→contracts [G] **nullable** §2.3, `document_id`). Standard columns + soft delete.
- **Permission:** curate `consultancy.booking_milestones.*` — SA/HT CRU, PM(a), **FA RU** (manages milestone amounts + payment status), SM read; the client reads milestones (amount shown per **W-14**, §2.4 — default hidden).
- **States / rules:** the enquiry→`confirmed` guard (10.1) succeeds **only** when a `milestone_type = confirmed` row is `done` **and** a signed contract exists (interim: a done `contract_signed` milestone + an uploaded signed-contract document) → **409 naming the missing item** otherwise (AC-05.6). Milestone **due/overdue** reminders are a new worker job following the reminder-job pattern (§1); `booking_milestone.due` / `booking_milestone.paid` events on the worker. **Payments are offline bank transfer in v1** — no Razorpay/webhook job; the milestone records the recorded payment, it does not collect it.
- **Tests:** e2e AC-05.6 (confirmed blocked with no milestone → 409; with the milestone but no contract → 409; with both → success, each 409 naming the missing item); the overdue-job test (idempotent, marks `overdue`, notifies once); authz rows.

## 6. Cross-cutting

- **Entitlement, not just permission:** consultancy is the existing **`hotel_assistance`** module entitlement (reuse `resolveClientEntitlements`) — **any one of** an active subscription, an active hotel-assistance `service_agreement`, or active project membership opens it (either/or, not both; `trial` is the one unhandled case, §1); payment activates only what was purchased. The new **per-enquiry chargeable gate** (10.2) layers on top. An **expired** account goes **read-only** (existing enquiries + saved **names** only, can still raise support requests); a **suspended** account is refused sign-in. Entitlement changes **never delete or hide records from AMPM staff** — they only narrow what the client reaches. Resolved in `entitlements.ts`, cached ≤ 5 min.
- **Denial equals absence** (the same 404 for forbidden and non-existent); **repository scoping mandatory** on every query (account/project membership, the `hotel_assistance` entitlement, soft delete); **ownership is looked up server-side, never trusted from the request**; no query bypasses the repository.
- **Visibility / money:** **RESTRICTED-FINANCE** — `hotel_proposals.internal_total_amount`; never serialised to client/demo/guest, excluded from exports except for FA and SA. **RESTRICTED-NOTES** — `hotel_enquiries.notes_internal`, `hotel_enquiry_events` with `internal_only = true`, `site_visits.outcome_internal`; staff-only. **RESTRICTED-CONTACT** — the whole of `hotel_contacts` (C) stays absent from client responses (AC-05.8). **CLIENT** — `client_total_amount`, `client_visible` lines, `functions_summary`, `notes_client`, `client_feedback`, enquiry status + non-internal events. **Margin is derived, never stored or sent.** One response model per audience; a field outside the principal's classes is **not sent at all**, never a hide-flag.
- **Product integrity:** **confirmed/firm quotations exist only in `hotel_proposals`** — indicative rate ranges (C) are never *presented* as confirmed. (The literal value `confirmed` is still the enquiry terminal status, a `booking_milestone` type and a site-visit status — the rule is about *pricing wording*, not the token.) **An enquiry is never a booking** (`confirmed` needs the done `confirmed` milestone + a signed contract). A proposal *decision* is **"accepted"**, not "confirmed".
- **Config, not code:** which `service_key`s are chargeable (R8), enquiry SLA days, milestone/label/status strings, and every fee **value** (entered, never defaulted) are `configurations`/reference rows. No hard-coded price, fee, category, colour or string.
- **Reuse the seams, don't rebuild:** read Module C (hotels, rate cards, media, `saved_hotels`) and Module B (accounts, subscriptions, entitlements) **through their services, never their tables**; **cross-module reactions go through domain events on the worker, never a direct upward call** — Module D **defines** `enquiry.created`, `enquiry.status_changed`, `site_visit.scheduled`, `proposal.shared`, `proposal.accepted`/`declined`/`expired`, `agreement.signed`, `booking_milestone.due`/`paid` (the architecture names no consultancy events yet; follow the §9 naming/worker pattern). The consultancy reminders (SLA, proposal expiry, milestone due) are **new jobs on the existing job seam** following the CRM reminder/expiry patterns — there is no existing overdue job to extend.
- **Audit** on create / update / **share** / **accept** / **decline** / close, every `service_agreement` status change, and every RESTRICTED-FINANCE read by a Super Admin outside Finance; before + after values; **no personal data in application logs** (`redact`).
- **Pre-merge (every feature):** diff vs `CLAUDE.md` + every rule file, each violation as `file:line` with the rule; then the invariants no linter sees — scoped repository on every query, every new permission curated from the matrix (no `provisional` left), data-model doc and schema agree, migrations expand before they contract, **no RESTRICTED field in a client view, no internal total on any client route, internal-only events absent from the client timeline.**
