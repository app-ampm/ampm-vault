## Verdict

The kernel, the policy package and the quality gates are in good shape, but the build is not yet deployable, and sprint 8 should pause after 8.1 for a hardening pass before 8.2 and 8.3, as it did on 27 October.

What holds:

- The gates are real. On the merged tree `pnpm check` runs 27 tasks green, the policy suite runs 9,868 cases, `authz:generate` reproduces the committed matrix byte for byte, Prettier and the tools tests pass, the web and API builds and the three mobile bundles succeed, and every infrastructure validator CI runs is green.
- The pipeline behaves as designed under live traffic: the envelope, the fixed parser wording, request ids, the 401 and 404 refusals, denial as absence for a client, 403 for a role that may read but not write, server-side sessions, the rate limit with `Retry-After`, no personal data in the API log, no `X-Powered-By`, and the public enquiry echoing only a first name.
- All six "fix before the next phase" items of 27 October were done, and the permission engine now agrees with the document on every row the reviewer probed.
- There is no `any`, no skipped test, no TODO without an issue and no committed secret in the tree.

What does not hold:

- **No email leaves a real deployment, for three independent reasons.** Under the BullMQ driver every notification enqueue throws, because the job id `notification.send:<uuid>` breaks BullMQ's custom-id rule (reproduced against the local Redis: the row stays `queued`, the queue stays empty); the invite paths swallow that error silently. The worker container has no outbound network. A failed send is terminal and nothing can re-send an invite. The first staff invitation on staging would never arrive and could not be retried.
- **A revoked session comes back after the hourly reap.** The reaper deletes revoked rows and the session service opens a fresh session for any verified token without a row, so revocation on a role change and the idle timeout hold for at most an hour while the token is valid (reproduced live).
- **An activated client has no wedding.** Nothing moves the membership from `invited` to `active`, and the principal loads active memberships only.
- **The only viewable feature cannot submit.** The website's Content Security Policy blocks the enquiry form's call to the API origin (reproduced in the browser), and the website has no deployment path at all: no Compose service, no Caddy block.
- **The bot check is a stub in every environment**, and the lead workspace lets any status move to any other, lets a client account own a lead, and answers 500 to a bad cursor or an unknown owner.
- **The deploy pipeline cannot run end to end as written** (no age key, registry login or repository credential on the host, no encrypted secrets committed), and staging and production publish the same host ports on the one VPS.
- **The repository process has three holes**: the main checkout is split from origin/main so every new worktree starts stale and every checkpoint push fails; the checkpoint hook never commits inside a worktree; and the knowledge graph has not been refreshed since pull request #22.

7. **Deploy and host.** Pin the age key path and create `/etc/ampm` in `bootstrap.sh`, add the GHCR login and a read-only deploy key for the repository, harden before cloning (F2, F11); separate the staging ports or run staging under its own Caddy site (F3); run Redis and Caddy as non-root (F4); gate the deploy on CI and on paths, and refuse a forward production deploy from `workflow_dispatch` (F6, F7).
8. **Process.** Fast-forward the main checkout and keep it on origin/main (P1); let the checkpoint commit in worktrees and scan before it pushes (F8, F9); refresh the graph (P2); add the web dependencies to CI's `web` filter (F10).
