## Narrative

This session continued the hotel-discovery pre-launch push across thirteen requests in one stream. It opened with **staff video upload** for hotel media (merged/deployed alongside the client Video tab), then a **detail-first Add-media modal** so staff add a media file and fill its details afterward through an Edit modal.

The question "what's the next demo-prep item?" led to **B9 — the CP-07 "Request hotel assistance" form** gaining Rooms / Contact-preference / Notes fields (pure frontend); merged as #128 and web-deployed.

The pivotal thread was **"Plan Gap 2"**. Research established that "Gap 2" is not a committed design term; the design's real pre-purchase demo experience is the **Demo Prospect (P-7)** — a `userType:"demo"` principal with its own entitlement and demo-visible hotels — and it is buildable now on the dev path (only real SMS-OTP is Cognito-blocked). The user chose to build that **canonical demo-OTP path** over a throwaway teaser, as a **6-slice plan**: (1) dev demo sign-in, (2) demo account+contact+lead, (3) Zoom-call → call_request activity, (4) saved_hotels reset in the nightly restore, (5) demo cap config, (6) the DM-01 demo banner.

**Slice 1 (#129, `523380a`)** minted the seeded demo principal: `DevLoginService.signInDemo()` + `POST /auth/dev-login/demo` (no schema/migration/contract change) + `useDemoSignIn()` + an "Explore the demo" dev-screen entry. The adversarial review caught a blocker — an e2e asserted `isDemo` inside `principal`, but `meResponse` puts it top-level (me.service.ts:42) — fixed before merge. Merged, API-first deployed (cross-stream: a peer session's #130 web-deploy already carried the frontend, so deploy-web.sh was skipped), verified live.

**Slice 2 (#133, squash `a7cbafb`)** gave the bare demo user a real backing: `upsertDemoAccount` seeds a Sales lead (`requested_demo`), a demo ClientAccount (`is_demo`, `lead_id` set, `primary_contact`=demo user) and a self AccountContact (`user_id`=demo user — the row `accountIdForUser` reads). Pure seed/baseline — no migration or contract change. Result: a signed-in demo prospect's saved hotels now persist, and a hotel-assistance request lands a `demo` lead activity on the lead and returns `routed_to_sales` instead of the old silent `no_lead` no-op. The review confirmed one latent test-isolation bug (a `demo` lead activity on an ON DELETE RESTRICT FK, left uncleaned, which could break demo-restore's rollback user-delete under a different Vitest file order — masked today by Vitest's larger-file-first ordering) and fixed it; three findings that mis-called it a deterministic CI failure were refuted. Because a seed change needs a full API-first redeploy, the box was re-seeded and verified on 127.0.0.1:7001: demo sign-in, `/me` type=demo, three demo hotels, enquiry → 201 `routed_to_sales`.

**What remains:** Slice 3 (the P-7 "Request a 15-20 min Zoom call" → a `call_request` lead activity), then Slices 4–6. The broader go-live blockers are platform/ops (client OTP via Cognito, the production VPS, S3+AV media, ~200 real hotels, the public marketing site, the pre-launch gates), tracked in docs/planning/hotel-discovery-go-live.md.
