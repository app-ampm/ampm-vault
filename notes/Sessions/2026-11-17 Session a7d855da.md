## Narrative

The user asked for a start-to-end walkthrough of the hotel discovery module (prospect to client) to present as a live demo. No code changed; the deliverable is a click-by-click demo runbook published as a private claude.ai page: https://claude.ai/artifact/VReVwxP2t2tQpxPVTveiU5 (styled in Peacock Night). It has nine acts (website enquiry → Sales qualifies and the demo preview → convert, sign up, Razorpay test payment → discovery, save, compare → request assistance → agreement and site visit → proposal and decision → contract and confirmation → finance and audit), plus an express run on Rhea's seeded Lake Pavilion enquiry, the enquiry status ladder, Q&A on what is real vs test stand-in, and troubleshooting.

It was built from three read-only code maps (client screens, staff screens, seed data and backend rules) and checked against the live box over SSH: the box API is at 9d247f2 and the web build at 2e8ff9d; PAYMENT_PROVIDER=razorpay (test keys) and earlier payments activated via the webhook; JOB_WORKER=true on the worker; Rhea's shared proposal is valid until 29 Nov 2026 and her plan to 5 Dec.

Demo traps recorded in the runbook: enquiry stages must be driven as Hema Hotels (HT), since SA/SM/FA are refused most moves; a lead converted live cannot sign in on the box (user is `invited`, no activation screen, console email), so the Sign up tab stands in for invite activation; converting needs an email on the lead; the demo account cannot buy a plan; Rhea has open enquiries on all four hotels, so a new request needs a fresh client; tabs in one browser window share the dev sign-in (use a normal window plus Incognito); proposal accept does not move the enquiry or notify staff; re-seeding resets Rhea's agreement, proposal and milestones but not the enquiry status.

Remaining (product gaps the demo works around, not started): invite activation screen, client notifications inbox, staff "New lead" button, editing visits and milestones after creation, logging Activity events from the app.

Follow-up the same morning: the user's lead "Yogesh" came in phone-only, so the Invite card showed only "Add an email before converting this lead" and the lead could not be converted. Built and shipped PR #149 (squash `1cca5f4`, web-only): the card now asks Sales for the email (validated with the API's `leadUpdateRequest`, saved via `PATCH /crm/leads/:id`), then offers "Create account and invite"; "Change email" corrects a typo; roles without `crm.leads.update` (HT, PM) see the warning instead; a 409 on convert now says "converted already, or this email already has an AMPM account". An independent review found 1 medium (a saved email could not be corrected) + 3 lows, all fixed. Deployed in full because #148 (activation screen, another session) was merged but not on the box: API redeployed from `a863bf3` (no migrations, re-seeded; `/auth/dev-login/invite` live), then web from `1cca5f4`. Left open: lead audit images do not record email/phone (needs a decision on storing them unmasked); invite emails are only logged on the box, which a separate session ("Make client invite links reachable on the test box") is working on.
