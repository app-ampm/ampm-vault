## Narrative

This long-running session built two modules of the AMPM platform end to end, slice by slice — each shipped
`pnpm check`-green behind an adversarial ultracode review and merged on its own PR with a monday.com trailer.

**Module C — Hotel intelligence (sprint 9).** The hotel discovery read-model (browse, search, filters, detail,
save, destinations, compare), rate cards with verifications and the freshness job, the media pipeline with
consented references, and the client rendering. Follow-ups hardened it: the `useHotel` detail-schema fix
(`hotelDetailView`, not a strict `hotelView`), and APPS-06 — an `apps/mobile` jest-expo test harness with a
hotel-detail regression guard, then account-screen state + offline-queue edge-case tests — closing the
"mobile has no test runner" gap. The build was re-verified application-deployable (D-060).

**Module D — Hotel consultancy phase-1 (sprint 10, features 10.1–10.5).** The consultancy half of Flow 2: a
discovered hotel becomes a negotiated, booked one. 10.1 the enquiry pipeline (the ten-status machine, the
append-only event timeline, the C→D entry); 10.2 service agreements + the config-driven chargeable gate
(AC-05.7) + the agreement→entitlement wiring; 10.3 site visits (dual-audience, hand-rolled machine); 10.4 hotel
proposals (the client/internal money split, the versioned/decision machine, `read_internal_amount`); 10.5
booking milestones + the AC-05.6 confirmed-guard + the overdue sweep. Internal costs, margins, internal notes,
hotel contacts and internal outcomes are provably ABSENT — not masked — from every client response; a demo
prospect routes to a Sales lead-activity, never into the pipeline.

**Decided and why.** R8 (which hotel services are chargeable) and R9 (the nine staff roles and who reads hotel
costs) were locked to their recommended, still-configurable defaults (D-064, D-065). The Module-D build
patterns were recorded this session: the enquiry state machine with in-service data guards (D-067), the
config-driven chargeable gate (D-068), per-audience response models with restricted fields absent not hidden
(D-069), the nullable-FK + in-module interim for the not-yet-built approvals/contracts/documents modules
(D-070), and hand-rolled status machines with compare-and-swap for the entities outside permission-matrix §7
(D-071). Every slice carried an adversarial review; the confirmed fixes — the draft-edit CAS on proposals, the
single-live-version guard, the P2002→409 mapping, the sweep-only `overdue` state, the richer milestone edit
audit, and the audited overdue sweep under a system context — were folded in before merge.

**What remains.** Module E (wedding projects) attaches by back-filling the nullable `project_id` on
enquiries/agreements/milestones; Module G (contracts) and Module I (approvals) attach to the nullable FKs and
interim mechanisms; Module N is still only the minimal documents layer (the confirmed-guard uses a plain
`document_id` reference meanwhile). Two review items are deferred to Module E: the enquiry-transition CAS
hardening (10.3, a concurrent double-advance) and the PM assigned-scope `read_internal_amount` project-target
fix (10.4) — both fail-closed today. The polished client/team screens (CP-07/08/09/10, TW-15/26/27/28) follow
visual-design approvals, and W-14 (whether the client sees a milestone amount) stays open, shipping as a config
flag defaulting hidden.
