## Narrative

**"Unable to reach server" on app.ampmverse.com was a fail2ban ban of the user's own IP, not an outage.** From the user's Mac, TCP 80/443 were refused (curl exit 7, `ECONNREFUSED`) while 22, 8443 and 5678 connected. On the box, nginx listened on 80/443, every AMPM container was healthy, and `/sign-in` (401 Basic-Auth) and `/_api/health` (ok, db ok) answered from the box itself. `~/logs/error_log` showed the trigger: at 03:58 UTC the browser made six sign-in calls in 13 s to `/_api/auth/dev-login*`, each rejected by Apache as `AH01614: client used wrong authentication scheme`. Plesk fail2ban (`/etc/fail2ban/jail.local`: 5 failures / 600 s, 600 s ban) banned 49.36.237.212, and the ban lifted on schedule at 04:08:39 UTC. Claude Code's WebFetch runs from the same Mac, so it was not an independent outside check.

**Root cause in the app:** the shared API client (`packages/api-client/src/client.ts`) attached the held access token to every request, sign-in included. An expired dev token was still in `localStorage` (`ampm.devToken`), and `/_api/auth/dev-login*` is the one API path kept behind Basic-Auth (D-080). An explicit `Authorization: Bearer` header replaces the browser's cached Basic credentials, so each click counted as a failed login.

**Fix (PR #147, branch `fix/sign-in-no-stale-bearer`):** `RequestOptions.anonymous` sends no Bearer and does not call the token getter. The five dev-login hooks (email, demo, request-otp, verify-otp, create-client) set it. All five routes are `@Public()`, so the API is unchanged; `/auth/activate` uses the token and is untouched. Tests came first: `client.test.ts` plus a new `hooks/use-dev-login.test.ts`, which fakes `useMutation` and the client so no renderer is needed; 6 failed before the fix and pass after. The secrets scan flagged `token = !anonymous` as a 10-char secret (a false positive), so the client returns early for anonymous requests instead of being allowlisted. The pre-existing `max-lines-per-function` warning on `createApiClient` (65 lines on main, now 70) was left alone. The deploy is web-only (`deploy/deploy-web.sh` from merged main); no API, contract or migration change.

**Merged and deployed:** PR #147 was squash-merged as `2e8ff9d` once CI was fully green (7 passing). It sits directly on `9d247f2`, which the box already ran, and went out as a web-only `deploy/deploy-web.sh` from merged main (bundle `entry-cbfb750a…`; all five sign-in calls carry `anonymous:!0`; `.htaccess` and `.htpasswd` intact). Before the deploy landed, the IP was banned a second time (04:13 UTC): signed in as staff, the user tried the client code sign-in, and the old bundle sent the VALID staff token to `request-otp`. So the bug was any held token, not only a stale one, and the fix covers both. Two bans in a day count toward fail2ban's `recidive` jail.

**Remains:** the broader stale-session behaviour (landing on `/sign-in` with a refused token still stored) is now harmless for sign-in, but the token is only cleared through the account screen. Unbanning needs root or Plesk admin (Tools & Settings → IP Address Banning), and repeat bans escalate through the `recidive` jail.
