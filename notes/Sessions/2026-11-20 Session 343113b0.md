## Narrative

A side session started from the production-cutover session to make the website's enquiry form (PUB-06) send a real Cloudflare Turnstile token. Production's API had just been set to verify every token with Cloudflare (`BOT_CHECK_PROVIDER=siteverify`), while the form still sent the placeholder `dev-bot-check`, so production refused every website enquiry with a 400.

**Built:** PR #156 on branch `feat/website-turnstile`, recorded as [[D-145]].
- The form draws Turnstile with explicit rendering, from a hand-written loader. No dependency was added.
- The code sits in `apps/web/src/components/contact/`: `turnstile.ts` (the loader and the typed slice of Turnstile's API), `bot-check.ts` (the check's states and the widget's lifecycle, with no framework code), `use-bot-check.ts` and `bot-check-field.tsx`.
- Send stays disabled, and dashed, until there is a token.
- The token travels as `botToken` and is spent the moment it is sent: the widget resets at once, so a send that fails waits for a fresh token.
- An expired token, a timed-out interactive challenge or an error drops the token, and Turnstile's own recovery runs the check again.
- A failed check shows a gold-glass notice, announced as `role="alert"`, with "Try the check again".
- Three more cases count as a failed check: a widget Turnstile refuses to draw (the self-review caught an unhandled rejection there), a widget drawn with no id, and a script that stalls for 15 s. An independent review agent found the last two before the merge, and found that the polite status line announced every token refresh. That line is now silent, and only failures are announced (`ec6e766`, `11ed012`).
- When the API refuses the token, the form shows a message of its own.
- `NEXT_PUBLIC_TURNSTILE_SITE_KEY` is read in `env.ts`, Zod-checked, and defaults to Cloudflare's always-pass test key.
- The website's CSP adds Turnstile's origin to `script-src`, keeping the nonce and `strict-dynamic`, and makes it the only `frame-src`. `connect-src` is unchanged.
- `web.Dockerfile` requires the key as a build argument. Both Compose examples that build the website pass it: production `0x4AAAAAAGKBfk9-4261LTAN`, and the always-pass test key for the test site.
- The two public keys are allowlisted in the secret scanner, and §4 of `docs/planning/production-readiness.md` is ticked.

**Why these choices:**
- **No reset from the error callback.** It would loop on errors that never clear, such as an unlisted hostname. Error recovery is left to Turnstile's back-off instead. A browser check with the always-fail key showed that Turnstile keeps retrying even though the callback returns `true`.
- **Spend the token at send time,** not after the API answers, so a token can never be used twice.
- **No wrapper package.** One would add a dependency for about 60 lines of loader, and the repository already loads Razorpay's checkout the same way.

**Verified:**
- `pnpm check` passes, all 28 tasks including the API's e2e suite. A fresh worktree needed `pnpm db:generate` and a throwaway database (`ampm_turnstile_test`, dropped afterwards). `format:check` also passes.
- The web app's tests went from 118 to 156.
- In the browser pane, a production build with the CSP enforced was run against a stand-in enquiry endpoint. The token was sent as `XXXX.DUMMY.TOKEN.XXXX` and the confirmation appeared. The refusal path, the failure notice with Try again, and the 1280px and 360px layouts all behaved as designed, with no CSP violations.
