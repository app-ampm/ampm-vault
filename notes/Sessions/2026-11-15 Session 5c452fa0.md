## Narrative

Started from the hotel-discovery session after the user opened "Open client account" from an enquiry on app.ampmverse.com and found a static page with no next step. Wireframe TW-13 describes the account page as "the commercial and access hub for one client"; the API had only convert, list and get for accounts.

**Agreed scope (with the user):** all five pieces — a Hotel enquiries section, a Service agreements section, a link back to the originating lead, Edit details, and add/edit contacts — plus both extras: removing a contact and inviting a contact to the portal. A contact who signs in keeps their email (the user chose to lock it rather than let the CRM copy drift from the login). Projects (Flow 3) stayed out.

**Built (branch `claude/account-hub`, cut fresh from origin/main 58ac4c8):** contracts in `packages/core` (`accountUpdateRequest`, contact create/update/result/removed, `accountId` on the staff enquiry list query); API `PATCH /crm/accounts/:id` and `/crm/accounts/:id/contacts` (add, edit, remove, invite), each `crm.accounts.*`-guarded and audited; a shared `AccountInviteService` that Convert now uses too; the staff enquiry list's `accountId` filter, kept out of the shared `filters()` so a client cannot widen their own list (pinned by an e2e). The mobile hub gains the sections, an Edit details sheet, a contact sheet with invite and remove, and hides each action from roles the server refuses, via `can()` from `@ampm/policy`. Decision recorded as [[D-134 Client account hub - contact edits, portal invites and the account enquiry filter]].

**Tests:** core schema tests, two new API e2e suites (account hub; account enquiries), pure form and permission tests, and screen tests for the hub. No migration and no permission-matrix change.

**Remains:** account status changes (suspend/close) and Finance billing on the hub; changing a portal user's sign-in email needs an identity flow; deploying needs a full API-first box redeploy (new endpoints).
