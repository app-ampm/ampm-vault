## Narrative

A side session started from the production-readiness session to close the partition item in `docs/planning/production-readiness.md` §4. `audit_events` and `notifications` were partitioned only to January 2027 and nothing created new months, so from February 2027 every row would have gone to the DEFAULT partition, where it also blocks creating that month's partition later.

**Built (PR #161, branch `feat/partition-maintenance`, decision [[D-150 Log-table partitions are kept six months ahead by a daily worker job]]):**
- Migration `20261120133309_partition_audit_notifications_2027` pre-creates February to December 2027. It uses the first migration's exact statements and is expand-only.
- The daily worker job `admin.partitions.maintain` (`apps/api/src/modules/admin/partitions/`, 02:30 UTC, recorded on `job_runs`) keeps the current month and the six after it.
- The job creates a missing month with the migrations' own DDL: lock the parent under a 5 s `lock_timeout`, check the catalog again, count DEFAULT's rows of the month, then create.
- It refuses, loudly, a month whose rows already sit in DEFAULT. It still creates the other months, records the run failed, logs `admin.partition_blocked` and throws. The manual fix (detach DEFAULT, create the month, move its rows, re-attach) is written in `docs/data-model.md` §3 and was tested on a throwaway database.
- Tests: unit tests for the month arithmetic, the SQL (checked statement for statement against both partition migrations) and the job's recording; four e2e tests (creates and no-op, refusal and recovery, lock timeout).

**Facts established:**
- Prisma ignores partitions that are not in a migration, so the job causes no drift.
- Production (read-only check): UTC, both DEFAULT partitions empty, the app role `ampm` owns the tables.
- Prisma 7's pg adapter sends DateTime values without an offset. On a non-UTC database (this Mac's Homebrew PostgreSQL in Asia/Kolkata) stored instants shift by the zone offset. CI and production run in UTC.

**Why these choices:**
- A worker job rather than pg_partman: there is no extension in the image, and the worker already has a scheduler and `job_runs`.
- Six months ahead leaves half a year to notice a failing job.
- Rows are never moved automatically: append-only audit rows stranded in DEFAULT need a person to look at them.

**Left:** the change takes effect with the next normal production deploy, whose migration step runs first; this session did not deploy. `graphify-out/` was not refreshed in the PR, to avoid conflicts with parallel PRs.
