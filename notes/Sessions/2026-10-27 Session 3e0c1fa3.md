## Narrative

This session took the Module A kernel from plan to landed-and-hardened, then opened the dynamic-RBAC workstream.

**Sprint-3 kernel (features 1–5), all behind adapters so Redis / live providers / Cognito are env swaps:** the typed configuration accessor; the job runner & event bus (BullMQ on Redis behind an Inline↔BullMq driver seam); the notification seam (adapter + console stub + service + in-app delivery + preferences); server-side sessions keyed by the token jti ([[D-033]]); and the audit-on-mutation pattern. Landed on main via PR #3 (features 1–3, merged early) and PR #6 (features 4–5 + hardening).

**Hardening ([[D-034]]):** transactional config audit; the hourly session reaper (scheduled only in the worker, so the API never blocks readiness on Redis); and monthly range-partitioning of `audit_events` and `notifications` (composite-PK + raw-SQL recreate, Prisma reports no drift; keyset pagination on uuid7 ids). Adversarial reviews caught and fixed the session first-use race, the audit null-image crash, the PII masker corrupting config images, and the Redis-at-boot coupling.

**R9 confirmed ([[D-035]]):** the nine staff roles and the drafted cost-visibility table are the system baseline (the updated 14-page brief re-lists R9 as still-to-confirm but does not change the set; the cost-visibility defaults remain AMPM's residual business call), which unblocks sprint-4 role admin.

**Dynamic RBAC decided ([[D-036]]):** after a nine-agent audit, chose catalog-gated dynamic RBAC — permissions-as-code / roles-as-data. The permission-key catalog, actions, scopes, conditions, the ten visibility classes and the nine system roles' default grants stay code (drift-checked, golden-pinned); custom roles, reusable permission sets and assignments become runtime data the API validates against a code-defined capability catalog and injects into the pure engine through a new `resolvedGrants` channel. Staff-only; a client/guest can never be elevated (structural ceiling). Supersedes A-6/P-1.

**Phase 1 built (dormant — no runtime behaviour changed):** `PolicyPrincipal.resolvedGrants` + the `decide()` union; the pure `catalog.ts` (680 grantable capabilities derived from the matrix, escalation-locking role/account admin + identity documents) and `capabilities.ts` (lookup + fail-closed `resolveCustomGrants`); `capabilities.json` emitted by the generator and covered by the existing matrix-drift CI check; `POLICY_VERSION` → 0.4.0. Verified: policy typecheck/lint/9,868 tests (golden suite untouched), API unit 91, API e2e 32 — all green.

**Remains:** the `visibility.ts` refactor (hardcoded per-role switch → capability-key-driven class resolution, proven byte-identical for the nine via a golden test) — deferred to its own verified step because it rewrites existing behaviour. Then the additive DB schema (`grantable_capabilities`, `role_grants`, `permission_sets` + joins), runtime wiring behind a flag, the SA admin 5-layer surface + audit read/export + a global staff-mutation audit interceptor, and retiring the lossy `role_permissions` mirror. Sprint 4 proper (user/role/membership admin) builds on this.
