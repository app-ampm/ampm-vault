## Narrative

This session took the Module A kernel from plan to landed-and-hardened, designed and shipped the entire dynamic-RBAC admin surface, then built out Module A's administration surface (staff users, invitations, client logins) — all merged to `main`.

**Sprint-3 kernel (features 1–5), all behind adapters so Redis / live providers / Cognito are env swaps:** the typed configuration accessor; the job runner & event bus (BullMQ on Redis behind an Inline↔BullMq driver seam); the notification seam (adapter + console stub + service + in-app delivery + preferences); server-side sessions keyed by the token jti ([[D-033]]); and the audit-on-mutation pattern. Landed on main via PR #3 (features 1–3) and PR #6 (features 4–5 + hardening).

**Hardening ([[D-034]]):** transactional config audit; the hourly session reaper (scheduled only in the worker, so the API never blocks readiness on Redis); and monthly range-partitioning of `audit_events` and `notifications` (composite-PK + raw-SQL recreate, keyset pagination on uuid-v7 ids). Adversarial reviews caught and fixed the session first-use race, the audit null-image crash, the PII masker corrupting config images, and the Redis-at-boot coupling.

**R9 confirmed ([[D-035]]):** the nine staff roles and the drafted cost-visibility table are the baseline (the cost-visibility defaults remain AMPM's residual business call), unblocking role admin.

**Dynamic RBAC decided and built ([[D-036]]):** catalog-gated dynamic RBAC — permissions-as-code / roles-as-data. The capability catalog, keys, scopes, conditions, the ten visibility classes and the nine system roles stay code (drift-checked, golden-pinned); custom roles, reusable permission sets and assignments are runtime data the API validates against the code catalog and injects into the pure engine via `resolvedGrants`. Staff-only — a client/guest can never be elevated (structural ceiling). Supersedes A-6/P-1.

**Foundation, phases 1–5 (dormant, merged PR #7):** phase 1 the `resolvedGrants` channel + pure `catalog.ts`/`capabilities.ts` (680 grantable capabilities, escalation-locking role/account admin + identity docs); the visibility switch kept, not rewritten ([[D-037]]); phase 2 the additive expand-only migration (`grantable_capabilities`, `role_grants`, `permission_sets` + join tables); phase 3 the idempotent seed from `capabilities.json`; phase 4 the audit backstop (global staff-mutation `AuditInterceptor` + `@Audited`/`@SelfAudited` markers + an architecture test that fails CI if a mutating route declares no audit); phase 5 the per-request runtime resolution behind `DYNAMIC_ROLES`. The phase-5 grant cache was dropped after an adversarial review found staleness/race/fan-out risks — resolution is per-request, so a role change is seen on the user's next request with nothing stale to invalidate. The matrix-drift CI failure (lefthook reformatting generated JSON) was fixed by prettier-ignoring the generated directory.

**Phase 6 — the Super-Admin admin surface, each slice built → `pnpm check` green → 3-lens adversarial review → fixes → PR → merge:**
- **6a role administration ([[D-038]], PR #8):** custom-role CRUD + user-role assignment; catalog allow-list on create and update, immutable system roles, system-role assignment requires SA, transactional audit + session revocation, 403/404 denial split. A resumed bug hunt found the "failing e2e" was a wrong expectation (PM holds `admin.roles.read`, so 403 — not 404 — is correct) and that the gitignored `apps/api/.env` had been lost (recreated with native-Postgres peer-auth strings).
- **6b permission sets ([[D-039]], PR #9):** reusable sets + attach-to-role, riding phase-5's union resolution (no migration, no resolution change); attach only to custom roles, idempotent attach; the escalation-lock guard extracted into a shared `capability-grants` helper used by both services.
- **6c audit read/export ([[D-040]], PR #10):** SA-only `GET /admin/audit-events` (filter + keyset pagination) and a self-auditing JSON `/export`; matrix-faithful (FA/PM denied fail-closed, not over-exposed); uuid-validated cursor. Phase 6 complete.

**Sprint-5 — the kernel finish (features 5.1–5.4), each contract-first → `pnpm check` green → 3-lens adversarial review → fixes → D-record → PR:**
- **5.1 Cognito-sandbox contract test + the [[D-041]] go-live gap ([[D-043]], PR #15):** an injectable-JWKS contract test pins the access-token shape and the verification algorithm, and the activation path now requires `email_verified` on the provider token — closing the go-live requirement that the Cognito access token carry a verified email (supplied by a Pre-Token-Generation Lambda).
- **5.2 notification templates ([[D-044]], PR #16):** per-channel rendering from `configurations` templates into a `RenderedContent` union; the render variables live on a server-only `notifications.data` jsonb column that is cleared after delivery (an adversarial review found an unbounded plaintext token otherwise sitting at rest).
- **5.3 real email over SMTP ([[D-045]], PR #17):** a nodemailer SMTP adapter behind the notification seam with a per-channel registry; the SDK import stays in the composition root, credentials come only from env, and a sanitized failure path never logs PII or leaves a row stuck `queued`.
- **5.4 rate limiting + CSRF/CSP + bot-check seam ([[D-046]], committed `4daeb2d`):** a hand-rolled ioredis rate limiter (atomic Lua window, principal/IP keying, fail-open on an outage, `Retry-After`) applied to `POST /auth/activate`; `TRUST_PROXY` now required in production so `req.ip` is the real client behind Caddy; hand-set API security headers; and a strict per-request nonce CSP on the web app with no inline scripts. The 3-lens review's real findings were all fixed — the silent proxy-IP trap (an env production guard), the untested production Redis path (unit-tested via a fake client, a malformed reply mapping to a safe zero count so limiting is never silently disabled), the header-only CSP test (now asserts the forwarded nonce), and a CSP bug a live browser check surfaced: a statically prerendered page shipped un-nonced scripts that `strict-dynamic` blocked, so the web routes are `force-dynamic` and hydration was confirmed to survive the policy. The bot check, a global rate-limit baseline, the API origin guard and public-form CSRF are deferred to the website sprint (recorded in [[D-046]]).

- **5.5 nightly demo-restore job ([[D-047]]):** a worker-only `DemoRestoreService` (the session-reaper model) resets demo data to a baseline the seed and the job share, in one guarded `$transaction` whose every delete is scoped to `user_type='demo'` — the guard baked into `DemoBaselineRepository` so no caller can omit it — recording a `job_runs` outcome (a new append-only model, the recorded outcome api.md wants). The canonical demo account is upserted at a fixed id, never hard-deleted (its FKs are RESTRICT and `audit_events` is append-only). It is a skeleton while the wedding-domain `is_demo`/`demo_visible` tables are still to come — each lands as one more reset spec and one more scoping-safety-test row. The 3-lens review hardened it: the scoping-safety test now covers all five cleared tables (it had proved only `sessions`, so an unscoped delete would have wiped real staff roles while staying green); `scheduleRepeatable` now threads each job's retry policy (a shared-infra gap that also fixed the reaper); and the failure path no longer masks the original error. The synthetic-data deletion exemption — demo rows are hard-cleared without the Super-Admin approval real-data retention needs — is recorded in [[D-047]].

Sprint 5 — the kernel finish — is complete (5.1–5.5): every Module A seam is a real, contract-tested provider path, the platform is hardened against abuse, the Cognito go-live gap is closed, and demo data self-restores. The kernel is done; the Phase-1 wedding-domain modules build straight on it.
