## Narrative

A side session started from the production-hardening session, to close two §4 items of [[production-readiness]] now that the API is public ([[D-148]]). Pull request [#162](https://github.com/app-ampm/ampm-platform/pull/162).

**Rate limits ([[D-149]]).** An inventory of every controller route found that only the auth routes, the website enquiry, plans, the Razorpay webhook and verify-payment had limits. The other routes a client, demo prospect or anonymous caller can reach had none, including the three the tracker named (hotel-assistance requests, portal subscribe, uploads), plus the public document-link and media-blob streams.

The decision was to limit all of them explicitly, and to make it stick with an architecture test. It mirrors the audit-coverage test and shares its controller discovery, now in `apps/api/src/policy/testing/` and kept out of the build. Rather than a silent default in the guard, every non-staff route must carry `@RateLimit` or a reasoned `@RateLimitExempt`. Only the health check is exempt.

The decorator gained two things:
- `perIpLimit`, a per-network window for signed-in callers, so one network cannot spread a burst over accounts;
- a required `failClosed`, so every route states what a Redis outage does to it.

Sign-in and the costly routes now fail closed with 503. Reads, sign-out, the payment confirmations and the webhook still fail open, so a Redis blip does not take the client app down. This supersedes [[D-046]] point 2 for the closed routes. The staff password throttle of [[D-142]] still fails open, but it now sits behind the fail-closed route limit.

**Subscribe.** It minted a Razorpay order and an initiated payment row on every call. It now hands back the subscription's newest order when:
- its payment is initiated or failed;
- it was made for the current price;
- it is under an hour old.

The hour bounds staleness, for example after the test-to-live key switch, which is now noted on the tracker. A unique index and a gateway status call were both rejected: the first needs a risky migration, the second a network call on every purchase.

**Staff sign-in race.** `verifyCode` compared before counting. The new e2e test reproduced seven compares against a five-try challenge. It now reserves each try first (`claimAttempt`, then `burnIfSpent`), as client codes do since the [[D-147]] review.

**Checks.** Twelve codes sent at once now compare exactly five times. `pnpm check` and `format:check` are green. The full e2e suite ran against a throwaway database.

**What remains:**
- the API deploy (API only, `redeploy-prod.sh`), not done here;
- edge limits in Apache, which need the server owner;
- a graph refresh with relabelling: the graph is stale across about 1,300 files, and the AST-only update re-clusters every community.
