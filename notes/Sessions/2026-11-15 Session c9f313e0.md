The user asked why Cognito was used. After I compared it with in-app sign-in, pointing to their LMS control plane, which signs people in itself, they chose to switch. That is D-142, built in PR #152:
- staff passwords with Argon2id from Node's own crypto, and RFC 6238 TOTP on Node's HMAC

- activation from an invitation sets both the password and the authenticator

- the session opens at sign-in, so a revocation reaches a token that has not been used yet (an e2e test caught this)
- the app's forms are shared with the old Cognito screen
- no new dependencies

**20 Nov 2026 (cont.): client sign-in by SMS code (D-147).**

The user asked for everything SMS delivery needs to be built now, with the provider wired later and the generated code shown on screen meanwhile. Built in #159 (`20c5d7b`):

  - Delivery goes through the notification pipeline (required, with the SMS address taken from `users.phone`).

  - Production refuses the console stub unless the on-screen code is on.

- **Independent review:** an adversarial reviewer found that the curtain did not cover `/_api`, so the on-screen code would have been open to the internet. It also found:
  - enumeration through the refusal messages;
  - a race past the five tries (reproduced at 38–39 comparisons);
  - lockout when two clients share a mobile;
  - timing;
  - limits failing open.

  All were fixed with tests before the first deploy: the client-code routes are now gated in the portal `.htaccess`, refusals are uniform, tries are reserved first, the shared-mobile case is refused, the code is sent after the answer, and the limits fail closed.
- **Also fixed:** a flaky D-142 test.
- **Deploy order:** the `.htaccess` first (verified 401 from outside), then the API (with the echo warning logged and an unknown number answered without a code), then the portal.
