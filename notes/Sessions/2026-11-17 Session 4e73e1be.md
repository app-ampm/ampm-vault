## Narrative

A side session started from the frontend-guide session to close the guide's §9.1 gap: invited staff and invited client contacts are emailed `/activate?token=…`, but no app had that route, so every invitee stayed `invited`.

The first finding changed the scope. `POST /auth/activate` (D-041) needs a provider access token as the Bearer, and under `IDENTITY_PROVIDER=local` (the test box) an invitee has no way to get one, so a screen alone could never activate anyone there. [[D-136 Invite links activate under the local provider through a dev-only stand-in for the provider sign-in|D-136]] records the choice: a dev-only `POST /auth/dev-login/invite` that checks the invitation without claiming it and mints a local token for the invited account, which the screen then presents to the real `/auth/activate`. It sits under `dev-login/` so the box keeps it behind Basic-Auth (D-080), and is sent anonymous like the other dev sign-ins.

Built on `feat/mobile-activation-screen`, PR app-ampm/ampm-platform#148: the `/activate` route and `ActivateScreen` in the sign-in arrangement ("Welcome aboard."), with ready, in-flight, activated, expired or used, already active, incomplete link and retryable-failure states, plus Cognito's sign-in-first; `ACTIVATION_ERRORS` in `packages/core` shared by API and screen; `RequestOptions.accessToken`, `useActivate({ token, accessToken? })` and `useDevInviteSignIn` in `packages/api-client`. `pnpm check` and `pnpm format:check` green (the secret scan caught one test literal, renamed). Verified in a browser against a local API: an invited staff user activated from the link, landed in the workspace, the reopened link said it was used, and dev sign-in by email worked afterwards.

Remains: merge #148, then an API-first redeploy of the box (new endpoint) followed by the web export, and a check on app.ampmverse.com. Follow-ups: a `returnTo` on the Cognito sign-in so an invitee need not reopen the link, and staff first-run credential delivery under Cognito.
