## Narrative

The user asked for a complete guide to the frontend: every working feature, and the workflows of both the admin (staff) side and the client side. Built `docs/guides/frontend-guide.md` on branch `docs/frontend-guide`, cut fresh from origin/main at `2e8ff9d` (this worktree's old branch was 47 commits behind), linked from `docs/README.md`, commit `95d3536`. Three parallel read-only traces (client portal; Sales, enquiries and Finance; admin console, hotel catalogue and website) were spot-checked in the code before writing. The checks covered the per-role area visibility, computed from the matrix's unconditional grants: SM does not see the Hotel catalogue, FA lands on Finance, CD/VC/RG/HL see only Tasks. They also confirmed that the Cognito sign-in is staff-only, that no handler acts on proposal accepted, and that there is no `/activate` route while dev sign-in and dev OTP accept only active users.

The guide covers the apps and their switches, sign-in (test build and Cognito), the role → area table and the client entitlement states, a screen-by-screen reference for both sides and the public site, workflows with Mermaid diagrams (all four parse and render with mermaid 10.9.1), a walkthrough with the seeded accounts on app.ampmverse.com, the status reference, and the gaps.

Gaps found that block a workflow step:
- No activation screen, so invited staff and converted-lead contacts cannot sign in on the test build.
- No client sign-in under Cognito.
- Enquiry Activity is read-only (the events POST has no UI), although the next-step text tells staff to log hotel replies there.
- No staff create or edit for leads, no staff subscription start, no destination create.
- The UI shows lead, enquiry and proposal actions that the server refuses for the role.

Not verified: whether the live site.ampmverse.com contact form reaches the test API (testing it would write a lead to the box). No PR opened; no D-record (documentation only).
